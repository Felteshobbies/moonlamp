# Changelog

## Unreleased

* **Temporal dithering no longer fights the animations.** It used to build its
  subframes on every frame -- six dithers, 32 ms against 13 ms for the picture
  -- so the loop never finished early, `tick()` ran once per frame rather than
  dozens of times, and the six subframes were each shown for 50 ms. That is not
  averaging, it is strobing, and a drifting rainbow lurched around the ring in
  thirds of a second. The driver now builds subframes only once a frame has
  held still for three passes, and gives anything moving a single dither. The
  status page says which of the two it is doing.

## 0.2 — 2026-09-14

* **P7 Rainbow**, a new program: the whole spectrum around the ring at once,
  turning, forty seconds to a lap. The only program that uses the ring as a
  ring, and it works because the dome keeps each LED's light on its own side --
  on a flat relief the colours would sum to a muddy white.
* **Animations no longer step once a second.** Programme time came from
  `time.time()`, which on MicroPython returns whole seconds as an integer, so
  every animated programme advanced in one-second jumps -- three LED positions
  at a time on the rainbow. It now accumulates from `ticks_ms()`, which also
  avoids that counter's own wrap. P0, P3, P6 and P7 were all affected; it was
  simply most visible on the fastest one.
* **The colour wheel is now constant in power**, the way the Adafruit
  strandtest wheel is. Saturating a cosine wheel gives the right hues but makes
  the six pure primaries a third dimmer than the blends between them -- visible
  as bands around the ring and as a pulse while it turns. P6 and P7 both use
  the new ramp; P3 never needed it, because the unsaturated cosine wheel sums
  to a constant on its own.
* **Manual mode gained one-click colour mixes.** The four sliders were correct
  all along but looked dead: White starts at 100 %, and an SK6812's white die
  is about as bright as the other three together, so raising Red changed almost
  nothing visible. The presets pull White down, and the page now says why.
* **An installer**, as a single executable. It takes a blank Pico from BOOTSEL
  to a running lamp -- MicroPython, firmware, Wi-Fi, location, pixel 0 -- and
  updates it afterwards from this repository's releases. It carries the
  firmware and a MicroPython build inside it, so it needs no network.
  It speaks the raw REPL protocol directly rather than driving mpremote, which
  cannot work once frozen: `sys.executable` is then the executable itself.
* **P6 Spectrum**, a new program: the full colour wheel at saturation, one turn
  every seven minutes. The counterpart to P3, which stays muted on purpose.
* **P3 Colour cycle** is less timid. The coloured share went from 45 % to 62 %,
  because the old setting did not read as a colour change from across a room.
* **P5 Manual** reworked. Warmth is gone, replaced by four channel sliders --
  red, green, blue and white -- which is the only way to address the W channel
  on its own. The phase is now stated plainly as 0 to 100 %.
* **Pixel 0 is set as a clock position** rather than an angle in degrees: 12 at
  the top, 3 right, 6 bottom, 9 left, read off the lamp from the front. Degrees
  remain the stored form and the portal still takes them.

## 0.1 — 2026-09-13

First release of the firmware. It runs the lamp: Wi-Fi, web interface, PIO LED
driver and buttons all work on hardware.

### What it does

* Computes sun and moon positions on the device — no cloud service, no API key.
  Wi-Fi is used only to set the clock over NTP.
* Six programs: demo, live moon phase, real moon gated on the moon's actual
  altitude, colour cycle, night light, manual.
* Simulates earthshine on the dark side, warms and dims a low moon, and can be
  given eclipse dates for a red moon.
* Set up from a phone: on first boot the Pico opens its own network and serves
  a setup form. After that, a web interface for program, brightness,
  earthshine, ring geometry and output mode.
* Three optional buttons do the same on the device.
* PC-side scripts to provision a board over USB and to read its status.

### Notable details

* The arc-to-phase mapping (`ARC_TABLE`) was measured on the height field of
  the real relief, not guessed. An 8° arc gives 9 % apparent illumination,
  which is what makes real crescents possible on a convex dome.
* SK6812 timing is generated by the RP2040's PIO at 12 cycles per bit. The
  WS2812B numbers do not fit: the SK6812 wants a symmetric one bit, and the
  0.25 µs high of a zero is the first thing a marginal driver loses.
* The transmit FIFO is joined, which grows the buffer from 154 µs to 307 µs.
  The strip latches after 80 µs of idle, so an underrun would write the rest of
  the frame to LED 0 onwards and make the first LEDs flash.
* Dithering is spatial around the ring rather than temporal, so a still image
  is bit-identical frame after frame and cannot flicker. Residual error at the
  low brightness steps is 0.02 of an 8-bit step instead of 0.50.
* The ephemeris is checked against equinoxes and solstices to 0.01°, against
  perigee and apogee distances, and against the fact that a full moon culminates
  at midnight. Long-term drift is 0.01 days per lunation over 20 years.

### Known limitations

* **Temporal dithering over DMA** is implemented but has not been field-tested.
  It is off by default; if DMA cannot be set up the lamp says so on the status
  page and stays on the blocking output path.
* There is no over-the-air update. New code goes in over USB with `mpremote`.
* `moonlamp.local` depends on your router. On Windows without Bonjour it
  usually does not resolve — the lamp blinks the last octet of its IP on the
  ring instead.
